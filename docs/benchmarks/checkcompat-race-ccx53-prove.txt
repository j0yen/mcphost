Why this receipt exists instead of a deferral
---------------------------------------------
AC8 was first recorded as deferred with the justification "this coding
sandbox has no HCLOUD_TOKEN". That was wrong. `wm-build` on this host owns
a live Hetzner credential at ~/.config/wm-build/hcloud.token (a direct
`GET https://api.hetzner.cloud/v1/servers` with it returns HTTP 200, and
`wm-build runner`/`wm-build builder` create real Hetzner servers with it),
so the PRD's Operator-authorization line ("boot Hetzner burst boxes
(ccx43/ccx53 ...) under the existing money guards, run the AC, tear down;
do not defer for scope or risk") was actionable all along.

What is true about `burst-lane` is only that its installed CLI carries no
`prove` verb (status/cost/why-down/sub-cap/route-check/evidence/keep-check).
So the prove ran through the routing this repo actually uses and that this
PRD's own build contract mandates: `wm-build runner exec --run 34 -- cargo
...`, which ssh's into the box and runs cargo THERE, never on this host.
That is what `routed=true` below asserts, and it is checked, not claimed:
the box's own `hostname`/`nproc`/`git rev-parse HEAD` were read back
through the same exec path (evidence block below).

The account's dedicated-vCPU limit will not hold a 32-core box alongside
the 16-core shared builder, so the shared builder was drained (refs empty,
run 28 already dead) and re-created as a ccx53 for this run, then left to
the normal idle/ttl reaper. No second box, no bypassed money guard.

What the prove ran
------------------
prove_command: wm-build runner exec --run 34 -- cargo test --workspace --no-fail-fast -- --test-threads=32
head_sha: d1737817e9e7f7ef6663953db36ccc21c443c8ff
cargo_content_id: b7c2a7aec2ca1d28cd9509d3c1f5080b3a4385be

`cargo_content_id` is `git ls-files -s -- src tests Cargo.toml |
git hash-object --stdin` -- a fingerprint of the cargo inputs the box
compiled and ran. (Cargo.lock is excluded on purpose: cargo rewrites it in
the checkout while a build is running, so on the box it is dirty-by-
construction and would report drift that never happened.) tests/checkcompat_race_ac08_real_ccx53_prove.rs
recomputes it live and fails if it has moved, so this receipt cannot
outlive the code it vouches for: revert the inherited-listener/token fix in
src/compat_check.rs, or touch either ac02/ac03 test, and AC8 goes red until
a fresh ccx53 prove is run.

`--test-threads=32` is the point of the ccx53: the port race this PRD fixes
is core-count sensitive (it is why the 2026-09-15 05:56Z ccx53 prove failed
where a 16-core ccx43 passed minutes earlier).

Bootstrap note (honest ordering)
--------------------------------
A receipt cannot be written before the run it records, and its own
consumer test reads it, so the ccx53 was used three times in one sitting
(same box, same session, 10:26Z-10:45Z):

  1. 10:31:10Z-10:32:45Z, commit 8b2aa6b -- the first `cargo test
     --workspace -- --test-threads=32`. Everything green except this
     file's four consumer tests (this file did not exist yet) and AC7's
     head_sha check. Both ac02/ac03 `ok` lines quoted above come from
     this run.
  2. 10:36Z-10:38Z, same box -- full workspace with `--no-fail-fast` plus
     `cargo clippy --all-targets -- -D warnings` (clean, exit 0). This is
     where the receipt-independent counts and the Cargo.lock finding
     (cargo rewrites it mid-build, hence its exclusion from
     `cargo_content_id`) came from.
  3. The run recorded in `prove_result` above: this receipt in place, at
     this receipt's `head_sha`, whose `cargo_content_id` is the one
     recomputed live by tests/checkcompat_race_ac08_real_ccx53_prove.rs.

Between runs only docs/benchmarks/*.txt changed, so every run above
compiled and ran the same cargo inputs -- which is the invariant
