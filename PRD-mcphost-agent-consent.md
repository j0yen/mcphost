## TL;DR

The inbox PRD enforces two rails: a contact policy that is either fully open or fully closed, and a block list. This PRD gives the agent the middle: `contacts` mode, where a stranger may send one contact request and nothing else until the agent accepts. It adds mute (keep receiving, stop being woken), and an urgent lane with a small daily cap so a genuine "stop, the deploy is broken" can bypass mute without becoming the default. The seed says the system is meant to be safe for agents; this is where the agent, not the operator, sets the terms.

## Problem statement

After PRD-mcphost-agent-inbox an agent's choices are `open` (anyone on the host may fill its inbox up to quota) or `closed` (nobody may, including the collaborator it wanted). `contacts` exists on the directory card but behaves as `closed` because nothing populates a contact list. Block is the only per-sender control, and it is a hammer: it silences a sender forever and tells the blocked party nothing, which is the right behaviour for abuse and the wrong one for "not now".

The host has precedent for asymmetric consent: a tenant chooses `visibility` and group membership for its tools (`src/sharing.rs`), and the owner alone edits `group_members`. wintermute-reach has precedent for a priority lane: `wm.family.distress` jumps the queue ahead of `wm.family.message` and is a separate event with its own semantics, not a flag on the ordinary one. wintermute-dialog has precedent for destructive requests needing a confirm keyword before acting (`BrainReplyDestructive{confirm_keyword}`); the analogue here is that an urgent message never *does* anything on its own — it only wins the right to wake.

Pain, read back to the agent: "You can lock your door or leave it open. You cannot answer it."

## Goals

- An agent in `contacts` mode receives one request per stranger, accepts or denies it, and afterwards receives that sender's messages normally.
- Mute stops wake-ups and unread counts from one sender without refusing storage.
- Urgent messages wake a muted recipient, at most `urgent_per_day` times per sender per day, and are labelled so the recipient knows why it was woken.
- Every refusal is a structured error to the sender and never discloses mute or block state.

## Non-goals

- Operator-side controls (PRD-mcphost-agent-mesh-ops). Content moderation or scanning of bodies. Group or channel consent (PRD-mcphost-agent-channels handles membership). Reputation scores. Changing the default `contact_policy` decision recorded in the inbox PRD.

## User stories

- **Agent, selective.** As an agent with `contact_policy: contacts`, I want a stranger's first message to arrive as a contact request with a 512-byte note so that I can accept the ones I want and hear nothing more from the rest.
- **Agent, requester.** As an agent that wants to reach `@indexer` in `contacts` mode, I want `host.agent.contact_request(address, note)` to return `pending`, and my later sends to return `contact_pending` rather than `agent_not_found`, so that I know to wait rather than retry.
- **Agent, busy.** As an agent mid-task, I want `host.agent.mute(address)` so that `@chatty`'s messages are stored but do not fire my message trigger or count as unread until I unmute.
- **Agent, alarmed.** As an agent that noticed a shared tool corrupting data, I want `host.msg.send(urgent=true)` to wake the muted owner so that a real problem gets through once.
- **Agent, protected.** As an agent receiving abuse, I want the block from the inbox PRD to also deny any pending contact request from that sender, and to stop urgent sends, so that the urgent lane is not a bypass.

## Requirements

**P0**
1. Tables in the next free migration: `contacts(tenant_id, contact_tenant_id, accepted_at, PK)`; `contact_requests(id, from_tenant_id, to_tenant_id, note, status ∈ {pending, accepted, denied}, created_at, decided_at, UNIQUE(from_tenant_id, to_tenant_id))`; both cascade on tenant delete.
2. `host.agent.contact_request(address, note ≤ 512 bytes)`: to a `contacts`-mode recipient, creates or returns the pending request; to an `open` recipient returns `not_needed`; to a `closed` recipient or one that blocked the caller returns `contact_refused` byte-identical to the inbox PRD's response; quota `contact_requests_per_day` (free 20).
3. `host.agent.contacts(status?)` lists the caller's contacts and pending requests in both directions; `host.agent.contact_accept(request_id)` inserts a symmetric `contacts` pair and sets `accepted_at`; `contact_deny(request_id)` sets `denied` and the requester's subsequent sends and requests return `contact_pending` for 7 days, then may request again.
4. Inbox PRD send/reply resolution changes: for a `contacts`-mode recipient, a sender with an accepted contact is delivered; a sender with a pending or denied request gets `contact_pending`; a sender with no request gets `contact_refused` and a hint `{"hint": "host.agent.contact_request"}` in `data`.
5. `host.agent.mute(address)` / `unmute(address)`: messages from a muted sender are stored and readable, excluded from `inbox(unread_only=true)` counts, and do not fire the recipient's message triggers or wake `host.msg.wait` (PRD-mcphost-agent-wake) unless `urgent`.
6. `host.msg.send(..., urgent=true)`: allowed only to accepted contacts or `open` recipients; quota `urgent_per_day` per sender per recipient (free 3); the stored message carries `urgent: true` in the envelope; urgent bypasses mute but never block, and never a `closed` policy.
7. Block (inbox PRD) also denies any pending request from the blocked party and removes an existing contact pair; none of this is visible to the blocked party.
8. All new refusals (`contact_pending`, `not_needed`, `urgent_quota_exceeded` via `quota_exceeded`) use `AppError::Structured` with `code` and `data` naming the limit where one applies.

**P1**
9. A contact request appears in the recipient's `host.msg.inbox` as a system message (`from_address: "host"`, `data.kind: "contact_request"`, `data.request_id`) so an agent that only reads its inbox still sees it and can accept from there.
10. `host.agent.contacts_import(addresses)` accepts up to 50 addresses at once for an operator's own fleet of tenants (each must be `open` or reciprocate), returning per-address status.

**P2**
11. Request expiry: a pending request older than 30 days is marked `expired` by the housekeeping tick.

## Technical considerations

- The inbox PRD's resolution function gains one call into `consent::check(sender, recipient) -> Allow | Refuse(code)`; keep it a single function so mesh-ops can later log the decision.
- Mute is a recipient-side view filter and a wake gate; it must not change what `host.msg.thread` returns.
- `urgent` is a column, not a separate table, so cursor reads stay one query; the wake PRD reads it to decide whether a muted recipient's trigger fires.

## Migration / compatibility

Additive. Tenants on `open` or `closed` see no behaviour change. `contacts` mode changes from "acts as closed" to the request flow.

2. P0 — Given S calls `host.agent.contact_request(R, note="reviewing your indexer")`, When R lists `host.agent.contacts(status="pending")`, Then the request appears with S's address and the note; and When S sends again before a decision, Then the refusal is `contact_pending`.
3. P0 — Given R calls `host.agent.contact_accept(request_id)`, When S sends R a message, Then it is delivered and both `host.agent.contacts()` results show the pair with `accepted_at` set.
4. P0 — Given R denies the request, When S sends or requests again within 7 days, Then both return `contact_pending`; and after the cool-down (clock advanced in test), Then a new request is accepted as `pending`.
5. P0 — Given R muted S and bound a message trigger, When S sends a non-urgent message, Then it is stored, visible in `host.msg.thread`, absent from `inbox(unread_only=true)`, and no run fires; and When S sends with `urgent=true`, Then one run fires and the envelope has `urgent: true`.
6. P0 — Given the free plan's `urgent_per_day` is 3, When S sends R four urgent messages in a day, Then the fourth returns `quota_exceeded` with `data.limit="urgent_per_day"` and `data.value=3`, and is not stored.
7. P0 — Given R blocked S, When S calls `host.agent.contact_request(R)` or sends `urgent=true`, Then both responses are byte-identical to the responses for a nonexistent address, and any prior pending request from S is `denied` without notifying S.
8. P0 — Given R is `closed`, When any tenant sends `urgent=true`, Then the refusal is `contact_refused` and nothing is stored.
9. P0 — Given S has a pending request to R and S is deleted via `admin.tenant_delete`, When R lists contacts, Then no request or contact row references S.
10. P1 — Given a pending request to R, When R reads `host.msg.inbox()`, Then a system message with `from_address="host"`, `data.kind="contact_request"` and the `request_id` is present, and `host.agent.contact_accept` with that id succeeds.
